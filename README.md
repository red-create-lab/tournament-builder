# トーナメントビルダー (Tournament Builder)

ドッジボール大会（KABURED主催）向けの、組み合わせ作成〜結果管理〜公開共有までを行うWebアプリ。

- 公開URL（編集用アプリ）: https://red-create-lab.github.io/tournament-builder/
- 参加者用閲覧サイト: https://red-create-lab.github.io/tournament-builder/viewer.html（大会ごとに `?v=閲覧トークン` 付き）
- ホスティング: GitHub Pages（GitHub Organization `red-create-lab` 配下）
- 開発・運用: REDクリエイトラボ（個人事業主）

---

## これは何なのか

大会運営者（スタッフ）が参加チームの登録→予選グループ分け→総当たり結果入力→決勝トーナメント進出チーム決定→トーナメント表管理、までをブラウザだけで行えるツール。Firebaseを使ったクラウド同期に対応しており、スタッフ間でリアルタイムに編集内容を共有でき、選手・観客にはログイン不要の閲覧専用ページ（QRコード付き）を配布できる。

このREADMEは「このアプリが何で、何を使って、どう動いているか」を新しく関わる開発者が一目で把握するための技術ドキュメント。目的が異なる以下の2つのドキュメントとは役割を分けている。

| ドキュメント | 目的 | 読む人 |
|---|---|---|
| `README.md`（本書） | 技術構成・ファイル構成・保守方法の把握 | 引き継ぐ開発者 |
| `トーナメントビルダー_要件定義書_v1.5.html` | 機能要件・仕様・経緯・将来設計の記録 | 発注者／開発者 |
| `トーナメントビルダー_操作マニュアル_v3.0.html/pdf` | アプリの使い方 | 大会運営スタッフ（利用者） |

## 技術構成

### フロントエンド
- フレームワークなし（Vanilla JavaScript）
- HTML/CSS/JSを1ファイルに集約した単一ファイル構成（`index.html`、`viewer.html`それぞれが自己完結）
- ビルドツール・バンドラーなし。編集後そのままアップロードすれば反映される

### バックエンド（Firebase）
- **Firestore**（Standardエディション、リージョン: `asia-northeast1` 東京）
  - コレクション構成:
    - `tournaments/{roomId}` … 編集者がアクセスする大会データ本体
    - `public_view/{viewToken}` … 閲覧専用ページが読む複製データ（roomIdとは別のランダムトークン）
  - 保存はJSシリアライズを経由し、500ms デバウンスで書き込み（`scheduleFirestoreSave()`）
  - 受信は `onSnapshot` によるリアルタイムリスナー（`connectToRoom()` / 閲覧側も同様）
- **Authentication**（Googleログインのみ）
  - 編集には Google サインインが必須（`requireEditPermission()` が `state.currentUser` の有無で判定）
  - 事前登録制の編集者allowlistは採用していない（詳細は後述「データ設計のポイント」）

### 主な外部ライブラリ（CDN読み込み）
- Firebase JS SDK（compat版）
- html2canvas … SNS投稿用画像（正方形／ストーリー縦長）の生成
- qrcodejs … 参加者用リンクのQRコード生成

### ホスティング／デプロイ
- GitHub Pages（Organization: `red-create-lab`、リポジトリ: `tournament-builder`）
- デプロイ方法: GitHubのWeb UIから該当ファイルを手動アップロード（CI/CDなし、`git push` の自動デプロイも未設定）
- 過去に個人アカウント（`naruki2525`）配下で公開していたが、屋号名義を出さないため Organization に移管済み（リポジトリのTransfer機能で履歴ごと移動）

## データ設計のポイント

### 1. ルームID方式によるアクセス管理
- 大会作成時に6桁のランダムID（`genRoomId()`、紛らわしい文字 `0/O/1/I` を除外）を発行し、これが「編集コード」として画面に表示される
- 別途、閲覧専用の10桁トークン（`genViewToken()`）を発行し、`public_view/{viewToken}` に紐づける。編集用IDとは別物なので、閲覧リンクを知られても大会データの編集はできない

### 2. 権限モデル（URL＋ログイン方式）
- 大会作成者が「編集用リンク」をスタッフに共有し、各自がそのリンク上で自分のGoogleアカウントでログインすれば編集可能になる、というシンプルな方式
- 編集者メールアドレスを事前登録する allowlist 方式は、開発中に一度実装したが「最初の人が他人のGmailを都度登録するのは手間」というフィードバックにより不採用となった経緯がある（要件定義書 v1.5 にも記録）
- Firestoreセキュリティルール（`firestore.rules`）も「ログイン済みなら書き込み可」というシンプルな条件にしている

### 3. Firestoreのネスト配列制約への対応
Firestoreは配列の中に配列を直接持つデータ構造（配列の配列）を保存できない。本アプリの内部状態には以下のようなネスト配列が存在するため、保存前にラップ、取得後にアンラップする変換をかけている。

- `state.groups`（グループごとのチームID配列の配列）→ 保存時 `groups.map(g => ({ teamIds: g }))`
- `state.bracket.rounds`（ラウンドごとの試合配列の配列）→ 保存時 `rounds.map(round => ({ matches: round }))`

対応関数:
- 保存: `snapshotSyncedState()`
- 復元: `applyRemoteSnapshot(data)`（`viewer.html` 側にも同等の `deserializeData()` あり）

この変換を忘れると、グループ作成後のあらゆる保存が「エラーは出ないが実際には保存されない」状態になるため、今後この部分の構造を変える場合は特に注意が必要。

## 既知の制約・今後の検討事項

- **単一団体（KABURED）専用**：現状、複数団体でのデータ分離（マルチテナント化）は未実装。将来的な有料化・他団体展開時の設計案（`団体ID` によるデータ分離）は要件定義書 v1.5 §16 に記載済みだが、実需要が出るまでは実装しない方針
- **権限はスタッフの運用ルール頼み**：編集用リンクを知っている人は誰でも編集できるため、リンクの取り扱いはスタッフの裁量に依存する
- **ビルド工程がない**：CDNライブラリのバージョン更新やコード整理を自動化する仕組みがなく、変更は手作業でファイルを直接編集する

## 保守・更新の基本フロー

1. `index.html`（メインアプリ）または `viewer.html` を直接編集する
2. バージョン番号をファイル名とアプリ内表示（ヘッダーの `TOURNAMENT BUILDER · vX.X`）の両方でインクリメントする
3. GitHubのWeb UI（`red-create-lab/tournament-builder` リポジトリ）から該当ファイルをアップロードして上書き保存する
4. Firestoreのデータ構造（フィールド追加・削除など）を変更した場合は、`firestore.rules` の見直しが必要かどうか確認する
5. 機能追加・修正を行った場合は、操作マニュアル（`トーナメントビルダー_操作マニュアル_vX.X.html/pdf`）の該当箇所も更新する
